## Dash — `C`

> **Superseded later the same day** — dash moved to `Ctrl` in the remap below.

| Constant | Value |
|---|---|
| `DASH_SPEED` | 18.0 (3× walk) |
| `DASH_TIME` | 0.3s (~5.4m of travel) |
| `DASH_COOLDOWN` | 0.6s (0.9s total press-to-press) |

- Direction is the current WASD input, or `transform.basis.z` (straight ahead) when standing
  still. The body snaps to face it on the start frame.
- Gravity still applies during the dash, so it works airborne and arcs down off a ledge.
  The dash owns horizontal velocity only.
- Blocked while crouching; blocks jump for its duration.
- Edge-detected in `_unhandled_input` (`not event.echo`) rather than polled, so holding `C`
  doesn't re-fire.
- **The clip is speed-scaled to fit the dash window**: `play("DASH", -1, clip_len / DASH_TIME)`.
  Authored at 1.0s against a 0.3s dash, that's 3.33× playback. Deliberate, and it means the
  animation stays in sync if the clip length ever changes on re-export.

## Sprint — hold `Shift`

- `SPRINT_SPEED = 9.0`, exactly 1.5× the 6.0 walk. Crouch wins over sprint (`Ctrl` clamps to
  3.0 regardless), so the speed pick became a small if/else.
- `SPRINT LOOP` replaces `RUN LOOP` as the locomotion loop via a `loop_clip` variable, so
  `RUN START` queues whichever matches.
- The steady-state branch only calls `play()` when the current clip is actually wrong, which
  lets toggling `Shift` mid-stride cross-fade over `LOCOMOTION_BLEND = 0.15s` instead of
  popping. That guard also self-corrects a `Shift` tap during the 0.25s `RUN START`: the
  queued clip goes stale, the next frame notices and blends to the right one.

## Double jump

- `MAX_JUMPS = 2`, tracked in `jumps_used`, reset on the floor.
- **The grounded jump still reads the held key** (`is_key_pressed`), preserving the existing
  hold-to-auto-bounce-on-landing feel. The air jump reads a *separate* edge-detected
  `jump_queued`. This split is the whole trick — without it, holding `Space` through the
  ground jump burns the second jump on the very next frame.
- Floor reset is gated on `velocity.y <= 0.0` so the launch frame doesn't clobber the count
  before liftoff.
- Walking off a ledge spends the grounded jump (`jumps_used = 1`), so a ledge drop grants one
  air jump, not two.
- Air jump **hard-sets** `velocity.y` rather than adding, so the second hop is the same height
  whether fired at the apex or halfway down.
- Restarting the clip needs `play("JUMP")` **followed by `seek(0.0, true)`** — Godot's `play()`
  resumes a clip that's already current instead of restarting it. The `true` applies the pose
  immediately so the flip re-fires on the press, not a frame later.

## Jump arc — phase-dependent gravity

The jump was a uniform parabola; it now runs three phases off `velocity.y`, in
`_gravity_scale()`:

| Phase | Condition | Scale |
|---|---|---|
| Launch | `velocity.y > APEX_BAND` (1.6) | **2.6×** |
| Hang | `abs(velocity.y) <= 1.6` | **1.0×** |
| Fall | `velocity.y < -1.6` | **1.0×** |

Heavy gravity on the way up is what sells the push-off: you leave the ground fast but bleed
that speed almost immediately, so it reads as an explosive shove running out of steam rather
than a lazy lob. Gravity then mostly lets go through the apex band.

Tuned in two passes (simulated at 60Hz before committing each):

| | `JUMP_VELOCITY` | Hang/Fall | Peak | Rise | Hang | Fall | Air time | Landing |
|---|---|---|---|---|---|---|---|---|
| Baseline (flat 1.0g) | 6.36 | — | 2.01m | 0.50s | 0.32s | 0.47s | 1.28s | 6.2 m/s |
| Pass 1 — reshape | 10.0 | 0.6× | 2.03m | 0.43s | 0.53s | 0.55s | 1.42s | 4.8 m/s |
| Pass 2 — taller + faster | **12.5** | **1.0×** | **3.03m** | 0.43s | 0.32s | 0.62s | 1.37s | 7.7 m/s |

Pass 1 deliberately solved `JUMP_VELOCITY` to land the peak within 2cm of the old 2.01m, so
the reshape alone changed *feel* without changing what geometry was reachable. Pass 2 then
took height to 1.5× on request and weighted the hang/fall back up.

Note the shape of pass 2: **50% taller but slightly *shorter* air time** (1.42s → 1.37s),
because the heavier hang and fall more than pay back the extra height.

`MAX_FALL_SPEED` (12.0 → 16.0) caps terminal velocity. A normal jump lands at ~7.7 m/s and
never reaches it; it only binds on long drops, keeping them at constant speed rather than
unbounded acceleration.

`HANG_GRAVITY_SCALE` and `FALL_GRAVITY_SCALE` are deliberately kept as two constants at the
same value, so the fall can be given its own weight later without touching the hang.

## Crouch — hold `Ctrl`

> **Superseded later the same day** — crouch moved to `C` in the remap below.

Speed (`CROUCH_SPEED = 3.0`) and the 1.8 → 1.0 capsule shrink already existed; this session
gave it a pose and fixed what that broke.

- `CROUCH START` → queue `CROUCH LOOP`, mirroring the `RUN START` → `RUN LOOP` pattern, driven
  off a new `was_crouching` latch. Crouch sits at the top of the locomotion branch so it
  outranks idle/run/sprint. Releasing `Ctrl` needs no special case — the existing branches see
  the mismatch and blend back out.
- **The model root no longer counter-drops.** The old
  `player_model.position.y = current_height - STAND_HEIGHT` was there to follow the shrinking
  capsule; the crouch clips animate the mesh down themselves, so it now double-dropped. The
  root only carries `RUN_MODEL_LIFT`.
- Fallout from that: `RUN_MODEL_LIFT` (0.08, which exists to stop the RUN clip's foot-down
  pose clipping the ground) was also applying while crouch-walking and floating her.
  `is_running` now excludes crouching.

### Freezing the crouch walk

`CROUCH LOOP` is a **crouch-walk cycle, not a static pose**, so it kept striding after the
player stopped. Fixed with `anim_player.pause()` — which holds the exact frame, and `play()`
with no arguments resumes it. Gated so `CROUCH START` always finishes, and keyed off `moving`
(which requires `is_on_floor()`), so a crouched ledge drop holds the pose too. No unpause path
is needed on release: every exit branch calls `play()` with a clip name, and that always clears
the paused state.

Freezing on the live frame then caught the **passing pose** — both legs in line, a stance
nobody holds. Measuring thigh separation across the cycle shows the clip is stepped, with four
held blocks:

| Time | Thigh separation | Pose |
|---|---|---|
| 0.042–0.208 | 32.0° | leg forward — good |
| 0.250–0.458 | 3.7° | legs in line — bad |
| 0.500–0.708 | 24.8° | other leg forward — good |
| 0.750–0.958 | 3.7° | legs in line — bad |

Fix is two lines: `seek(0.0, true)` then `pause()`. The first key sits at t=0.042 and Godot
clamps anything earlier to it, so frame 0 *is* the 32° widest-separation pose — the strongest
of the four to stop on.

A more elaborate version was built first and thrown away: scanning the thigh tracks at runtime
to derive both contact poses and snapping to whichever was nearer, so it would survive a
re-export that retimed the walk. Frame 0 makes ~50 lines of that unnecessary. Recorded here in
case a future re-export moves the good pose off frame 0 — that's the trigger to reconsider.

every crouch and read as bobbing. Now pinned to `STAND_HEIGHT` — the camera sits at the same

## Known issues / next steps

- **`STOPPING` is unwired.** A 1.0s deceleration clip, but the controller currently halts in
  about one frame (`move_toward(velocity, 0, speed)`). Making it read means giving the stop a
  real deceleration window and holding movement lockout during it — a genuine feel change, not
  just an animation hookup. Open question: proper stop-and-settle, or play it cosmetically over
  the instant halt.
- **Standing up under a low ceiling isn't blocked.** Release `Ctrl` in a 1.0m gap and the
  capsule grows back to 1.8 inside the geometry, shoving or wedging the player. This is exactly
  the scenario crouch-walking exists for, so it will come up. Fix is a short `ShapeCast3D` above
  the head that holds the crouch while blocked.
- **Crouch always settles on the same leg**, and resuming replays from the cycle start rather
  than continuing. Reads fine on a stepped clip; if repeated stop-starts look mechanical,
  alternate between frame 0 and the ~t=0.60 contact pose.
- **No crouch-idle clip.** A stopped crouch is a frozen walk frame. Works, but a dedicated
  static pose would be better.
- **Sprint stride isn't scaled to speed.** `SPRINT LOOP` plays at 1× while covering 1.5× the
  ground. If the feet skate, scale playback by `speed / SPEED`.
- **Sprint works in every direction**, including strafing and backpedalling. Easy to gate to
  forward-ish input if that's wrong.
- **The double jump uses the same `JUMP_VELOCITY`**, so a full chain now clears roughly 6m
  (up from ~4m). If that overshoots level geometry, add a separate `AIR_JUMP_VELOCITY` rather
  than lowering the first hop.
- **Camera pivot is fixed while the model drops.** At a steep downward pitch while crouched,
  Setsuna frames slightly lower than she used to. If that reads oddly, offset the spring arm
  rather than reintroducing pivot movement.
- **Movement input is still all raw keycodes** (`KEY_C`, `KEY_SHIFT`, `KEY_CTRL`, …). The UI
  work later today put the *menu* inputs on real InputMap actions, so the project now runs a
  split convention. Deliberate — see the UI session below — but it is the thing to collapse
  before rebinding ever matters to a player.

# Session 2 — control remap + the first UI

Second session of the day. Split in two on purpose: the key remap shipped and was checked
**before** any UI existed, so a movement regression could not hide inside a UI change.

## Control remap

`C` and `Ctrl` swapped, and `F` picked up a second job.

| Key | Was | Now |
|---|---|---|
| `C` | dash | **crouch** (toggle) |
| `Ctrl` | crouch | **dash** |
| `F` | enter / exit Exia | **also confirm in menus** |

`Shift` stays sprint; `Space` stays jump; WASD untouched.

The trap here is that **crouch and dash are read in deliberately different ways**, and the
reading style belongs to the *action*, not the key. Crouch is a polled edge
(`is_key_pressed` + `crouch_was_pressed`), specifically so it doesn't depend on an event
reaching `_unhandled_input`; dash is a true `not event.echo` event. Swapping keys means
carrying each style across with its action — swap the reading style too and you reintroduce
the exact bug the comment on the crouch block exists to prevent.

Also gone: **the `Esc` mouse-capture toggle** in `player.gd`. Pause releases the cursor anyway,
so it was fully subsumed. Leaving it would have been an active bug rather than dead code — the
pause screen consumes `Esc` before `_unhandled_input` ever sees it, so dismissing a menu could
recapture the mouse and then immediately re-toggle it back off.

`mech.gd` crouch moved to `C` in the same pass.

## Crouch no longer brakes you in the air

Reported after the UI landed, fixed in the same session. `player.gd` picked `CROUCH_SPEED`
whenever `crouching` was true, floor or not, so tapping `C` mid-jump dropped horizontal speed
from 6.0 (or 9.0 sprinting) to 3.0 and visibly killed the arc.

```gdscript
var speed := SPRINT_SPEED if is_sprinting else SPEED
if is_crouching and is_on_floor():
	speed = CROUCH_SPEED
```

Airborne crouch is now purely a pose. **The collider and mesh still shrink in the air** — only
the speed penalty is gated. So ducking mid-jump is a smaller hitbox at full speed, which is
either a free mechanic or a way to slip through gaps you shouldn't; left as-is until it
actually causes a problem.

# The UI system

Spec written first, at [specs/ui-system.md](../specs/ui-system.md) — it carries the palette,
the full state table, and the options that were rejected along with why. This entry records
what was built and what was learned building it.

## Shape of it

| File | Role |
|---|---|
| `resources/ui_theme.tres` | Every colour, stylebox, and font size. One file. |
| `scenes/ui/ui_window.tscn` + `scripts/ui/ui_window.gd` | The reusable frame both screens instance. |
| `scenes/ui/pause_menu.tscn` + `scripts/ui/pause_menu.gd` | Dim + shrink-to-fit window, four entries. |
| `scenes/ui/inventory.tscn` + `scripts/ui/inventory.gd` | 900×600 empty frame with a close button. |
| `scripts/ui/ui_manager.gd` | Autoload `UI` — screen state, pause, cursor. **First autoload in the project.** |

Measured on boot: pause shrink-fits to **394×266** (360 min-width menu + 2×16 content margin +
2×1 border), inventory holds **900×600**.

## Two screens, two different relationships with time

| | Pause | Inventory |
|---|---|---|
| Key | `P` | `Tab` |
| World | frozen (`tree.paused`) | **running** |
| Screen | 60% dim, full-screen | no dim, centered popup |
| Camera | n/a | **dead** |
| Movement | n/a | **live** |

`P` reaches pause from anywhere including the inventory; `Tab` while paused is ignored, because
both alternatives contradict a decision made elsewhere (either unfreeze the world, or show a
non-pausing screen over a frozen one). `Esc` closes whatever is open, and is left unconsumed
when nothing is.

## The findings worth keeping

**Releasing the cursor disables the camera for free.** `player.gd` and `mech.gd` both gate
mouse-look on `Input.mouse_mode == MOUSE_MODE_CAPTURED`, while WASD is polled and *ungated*. So
"can walk, can't look" — the exact requested behaviour for the inventory — falls out of the
existing controllers with **zero changes to either**. The planned `input_enabled` gate turned
out to be unnecessary.

**`Space` had to come off `ui_accept`; `F` was safe.** Mirror images of each other, and the
reason is which side of the input system each key is read on:

- `player.gd` polls `Input.is_key_pressed(KEY_SPACE)` for the grounded jump inside
  `_physics_process`, which **never sees events**. A focused `Button` consuming the Space
  *event* does nothing to it — so confirming a menu item would also make Setsuna hop. Space is
  now stripped from `ui_accept` in `project.godot`.
- `mech.gd` reads `F` as an **event** in `_unhandled_input`. A focused button consuming it
  correctly suppresses enter/exit Exia. `F` is collision-free by construction.

The general lesson: **polled input cannot be blocked by UI.** Any future "block gameplay while a
screen is open" has to be an explicit gate in the controller, not a focused Control.

**Menu navigation can't live on WASD**, because the inventory doesn't pause — `W` would walk the
player while moving the cursor. Arrow keys and the D-pad are the only conflict-free option.
Mouse is the expected path anyway; the D-pad bindings exist so a controller isn't dead in menus.

**`_input`, not `_unhandled_input`, and consumed.** `Tab` is Godot's built-in `ui_focus_next` —
any focused `Control` would eat it before the inventory ever saw it.

**The autoload's `process_mode` is load-bearing.** `PROCESS_MODE_ALWAYS`, or the pause menu
pauses the node that owns it and nothing can unpause it.

**The chrome is built in code, not saved into the scene.** `ui_window.gd` assembles header +
content in `_build()` and re-homes whatever the screen scene parented to it. That keeps the
screen scenes free of editable-children paths reaching into the window's internals — but it
means `ui_window.gd` **must not be `@tool`**: it reparents nodes the screen scene owns, and
doing that in the editor risks serialising them at their moved path.

## The bug the tests didn't catch

`pause_menu.gd` found its buttons with `find_children("*", "Button", …)`. That search also
reaches **the window's own close button**, which sits ahead of the menu in tree order (header
before content). `focus_first()` would therefore aim at the header — and because the close
button is `FOCUS_NONE`, `grab_focus()` silently did nothing, leaving the menu with no focus at
all. Exactly the kind of failure that looks fine on a mouse and is dead on a controller.

Filtered on `focus_mode != FOCUS_NONE`. Verified with a throwaway `SceneTree` script that
`focus_first()` lands on `Resume`.

Worth recording separately, because it cost a debugging round: **`_ready` has not run on a node
you just `add_child`ed during `_initialize()`**. `is_node_ready()` was `false` and `content` was
`null`. The first check script concluded the window was broken when it had simply not been built
yet — the assertions had to wait a frame.

## Tests

Two new files, **35 tests / 168 checks** passing overall.

- `tests/test_ui_manager.gd` — the transition table. `resolve(current, action)` is a **pure
  function**: no nodes, no tree, no side effects. Two reasons. It's the only part of this work
  that can be *silently* wrong (a cursor that never recaptures, a world stuck paused), and it
  sidesteps whether autoloads are even instantiated under `--script`.
- `tests/test_ui_theme.gd` — expected colours come from the spec, never from reading the `.tres`
  back, per the existing convention.

## Known issues / next steps

- **"Back to Main Menu" cannot work** — there is no main menu scene. It and "Options" are stubs
  that print a line. Resume and Quit to Desktop are live.
- **The inventory is empty by design**, so it can't validate the theme. Scrolling, long labels,
  row separators, and an empty state are all untested. Expect some values to move once there is
  real content.
- **`F` falls through to gameplay when nothing has focus.** With the inventory open and no
  button focused, pressing `F` near Exia will mount or dismount. Harmless while the inventory is
  empty — nothing can take focus — but it needs a decision once it has clickable contents.
- **The grain keeps moving while paused.** The compositor advances its seed per *rendered*
  frame, and pausing doesn't stop rendering. Left deliberately: live grain over a frozen frame
  reads as a printed page.
- **UI gets no post-processing at all.** `CompositorEffect` runs on the 3D render; a
  `CanvasLayer` draws over the finished frame. No outline, no grain, no fog on any menu. The
  warm-tinted greys (`#3A3532` body, `#1A1410` ink instead of pure black) are what keep that
  contrast reading as deliberate rather than as a default engine overlay.
- **Split input convention** — UI on InputMap actions, movement on raw keycodes. Accepted for
  now; migrating a 300-line controller that was just tuned is its own change.
- **Airborne crouch still shrinks the collider** (see above).
- **`ZoneManager` will be the second autoload.** `UI` was built global from the start
  specifically so pause survives the scene swaps that system will do.
